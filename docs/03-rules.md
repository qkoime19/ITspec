# 3. Бизнес правила

Ред на предпочитание за мястото: ограничение в базата → процедура с транзакция → проверка в API. Колкото по-близо до данните, толкова по-трудно се заобикаля.

| # | Правило | Къде се пази | Защо там | Тест → очакван резултат |
| --- | --- | --- | --- | --- |
| 1 | Имейлът е уникален | UNIQUE индекс (+ проверка в AuthService) | пази и при две едновременни регистрации | втора регистрация → 409 (SQL T1) |
| 2 | Ролята е Client, Technician или Admin | CHECK | грешна стойност не може да влезе по никакъв път | INSERT с роля Boss → грешка 547 (T2) |
| 3 | Ролята не идва от front-end-а | API: отделни адреси register/client и register/technician; DTO няма поле Role | ролята не трябва да е избор на потребителя | "role": "Admin" в тялото → 201, но като Client |
| 4 | Admin не се регистрира | миграцията (HasData) | администраторът съществува от създаването на базата | няма адрес за регистрация на Admin |
| 5 | Оферта само по Open заявка | API (OfferService) | проста проверка преди запис | оферта по Assigned заявка → 409 |
| 6 | Техникът предлага само в своите видове устройства | API + таблица TechnicianDeviceTypes | изисква връзката N:M | оферта извън вида → 403 |
| 7 | Един техник — една оферта на заявка | UNIQUE (SupportRequestId, TechnicianId) | пази и при едновременни заявки | втора оферта → 409 (T3) |
| 8 | Най-много една приета оферта на заявка | **usp_AcceptOffer** (заключване) + филтриран UNIQUE индекс | промени в няколко реда наведнъж; индексът е втора линия | второ приемане → 409 (T7, T10) |
| 9 | Клиентът приема оферта само по своя заявка | **usp_AcceptOffer** (ClientId от токена) | проверката е в същата транзакция като промяната (защита от IDOR) | чужд клиент → 409, нищо не се променя (T8) |
| 10 | При приемане: офертата Accepted, другите Rejected, заявката Assigned | **usp_AcceptOffer** с транзакция | три промени — всички или нито една | T9 |
| 11 | Завършва само техникът с приетата оферта, само Assigned | API (RequestService) | проста промяна в една таблица | друг техник → 403; грешен статус → 409 |
| 12 | Прекратява само собственикът, само Open/Assigned | API (RequestService) | проста промяна; чакащите оферти стават Rejected в същото SaveChanges | чужда → 403; втори път → 409 |
| 13 | Отзив само за Completed, само за своя, веднъж; рейтингът се обновява | **usp_AddReview** с транзакция + UNIQUE (SupportRequestId) | две таблици наведнъж (Reviews и Users) | преди Completed → 409 (T11); втори → 409 (T15) |
| 14 | Оценката е от 1 до 5 | CHECK + DTO валидация + процедурата | три нива: API (400), процедура (50007), база (547) | оценка 7 → 400 (T6, T12) |
| 15 | Видовете на техника се сменят изцяло, само с активни видове | **usp_SetTechnicianDeviceTypes** + табличен тип | списък като един параметър; всичко или нищо | несъществуващ вид → 409, старите остават (T16) |
| 16 | Адресът и телефонът на клиента не се виждат, докато офертата не е приета, и тогава само от приетия техник | API: DTO (RequestService.GetDetailsAsync); изгледите нямат тези колони | скриване с JavaScript не е защита | детайли преди приемане → null; друг техник → null (T19) |
| 17 | Блокиран потребител не влиза | API (AuthService) | проверка при вход | вход с блокиран → 403 |

## Собствено правило

| | |
| --- | --- |
| **Правило** | Техник не може да има повече от **3 поети (Assigned) заявки едновременно**. Ако клиент се опита да приеме оферта на техник, който вече има 3 незавършени поръчки, приемането се отказва и клиентът трябва да избере друга оферта. |
| **Защо е свързано с темата** | IT ремонтите отнемат дни (чакане на части, преинсталации). Техник, който поеме твърде много поръчки, бави всички клиенти. |
| **Къде се пази** | В процедурата **usp_AcceptOffer**, в същата транзакция като приемането (грешка 50005 → HTTP 409). |
| **Защо там** | Броят се изчислява от няколко реда в две таблици, затова не може да е CHECK. Ако е само в API, двама клиенти, които приемат оферти на същия техник в една и съща секунда, ще видят по 2 поети заявки и ще го натоварят с 4. В процедурата редът на техника се заключва (UPDLOCK), така че втората транзакция чака първата и вижда вече 3. |
| **Как се тества** | SQL: тест T18 в `05_tests.sql` (техник с 3 поети заявки, приемане на четвърта → 50005, заявката остава Open). API: приемане на оферта на такъв техник → 409 със съобщение „Техникът вече има 3 поети заявки…“. |
